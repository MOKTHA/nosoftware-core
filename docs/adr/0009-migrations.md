# ADR-0009: Migrations — Forward-Only with Reset as Phase 1 Reversibility

**Status**: Accepted
**Date**: 2026-07-09
**Author**: Architecture Team
**Superseded By**: N/A

## Context

Phase 1's exit criterion requires that *migrations be repeatable and reversible*.
drizzle-kit's `generate` command produces forward-only SQL migrations — it does
not synthesize `DROP` statements or a paired "down" script. Down migrations must
be written manually, a non-trivial effort per migration that includes data-aware
operations (column renames, enum additions, table splits) that can lose data.

The migration set in Phase 1 is small (three migrations: schema bootstrap,
invitations table, audit_entity_type extension) and the local dev database is
disposable. Production data does not yet exist.

## Options Considered

### Option A — Hand-write down migrations for every forward migration
* Write `0000_down.sql`, `0001_down.sql`, `0002_down.sql` that drop the
  objects introduced and any dependent indexes/FKs.
* Pros: satisfies "reversible" in the strictest sense.
* Cons: manual maintenance burden per migration. Risk of data loss on real
  production databases once user data exists. Not automatable in CI without
  a separate rollback pipeline.

### Option B — Treat `pnpm db:migrate:reset` as the reversibility mechanism
* `db:migrate:reset` drops all tables and reapplies the full forward set.
* Use this in dev + staging; document that production rollbacks are handled
  via backup + restore, not migration down paths.
* Pros: zero manual maintenance. No data loss in the local dev cycle.
  Matches how most teams use drizzle-kit in practice.
* Cons: doesn't satisfy strict reversibility — the dev DB loses everything,
  not just the most recent migration.

### Option C — Defer reversibility entirely to Phase 9
* Document the current state as-is, explicitly noting that reversibility is
  out of scope for Phase 1.
* Pros: no work now.
* Cons: leaves the exit criterion half-met.

## Decision

**Option B** — accept that `pnpm db:migrate:reset` is the Phase 1 reversibility
mechanism. Phase 1's exit criterion *"Migrations are repeatable and reversible"*
is met when:

- **Repeatable ✅** — forward migrations are generated by drizzle-kit from the
  schema definitions and are deterministic. Running `pnpm db:migrate` on a
  fresh database produces the same schema regardless of the path taken.
- **Reversible ✅** — `pnpm db:migrate:reset` drops and re-applies the full
  forward set. This is the accepted mechanism in dev and staging environments.
- Production-grade down migrations (hand-written, data-preserving) are a
  Phase 9 governance concern — introduced alongside backup/restore runbooks,
  tenant-isolation hardening, and the approval workflow.

### What Is Not Being Done in Phase 1

- Hand-written `*_down.sql` files.
- A CI job that exercises rollback.
- A production-tenant-aware rollback path (covered by Phase 9 ADR on audit /
  backup).

### Why This Is Acceptable Now

1. Phase 1 data is synthetic (seed script + dev Postgres via docker-compose).
   No production tenant has data at the time of Phase 1 sign-off.
2. The migration set is small and the schema is stable — the chance of needing
   a down migration in Phase 1 is near zero.
3. drizzle-kit's `migrate` is forward-only by design; adding manual down files
   creates a second source of truth that can drift from the forward set.
4. Phase 9's governance stream is the natural home for production rollback
   policies — introducing ad-hoc rollback in Phase 1 would be premature.

## Consequences

- Positive: Phase 1 closes faster; the governance concern is not lost — it's
  explicitly tracked as a Phase 9 item.
- Negative: if a data-preserving rollback is needed before Phase 9 hardening,
  the team must reconstruct it from git history and the schema state at that
  revision. This is acceptable for Phase 1 risk profile (no production data
  to lose).
- The `scripts` section in `packages/persistence/package.json` already exposes
  `db:migrate` (forward) and `db:migrate:reset` (drop + reapply). No code
  change needed; this ADR documents the accepted usage.

## Phase 9 Follow-up

Phase 9 governance will:
- Introduce a `docs/ops/rollback.md` procedure covering both automated (drizzle
  down) and manual (backup-restore) rollback paths.
- Add hand-written down migrations for each Phase 1-8 migration at the boundary
  into Phase 9 (data is live; rollback must be tenant-safe).
- Extend CI with a `rollback-smoke` job that exercises forward-then-backward
  against a test database.
- Audit the `pnpm db:migrate:reset` surface: confirm it isn't exposed in any
  environment where user data exists.
